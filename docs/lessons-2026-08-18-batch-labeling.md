# 经验教训:221 张真实投影白板批量标注(2026-08-18)

来源:第一批真实数据 ingest → 标注 → 出片 → 评测全流程。数据集定稿 218 张
(`spike/photos-batch/`,gitignored)。工具已升格为 `desktop/server.js` + `desktop/ingest.js`，
私有数据仍留在原目录并通过 `--data spike/photos-batch` 显式选用。

## 1. 比例校验:标注时即时提示,不等人翻成品

**教训**:IMG_4083 的框圈到了墙上、IMG_4091 标偏,都是事后扫 outputs 宽高比才发现的。
投影幻灯片有强比例先验——**218 张实测成品 ar 均值 1.96、σ 0.02**(16:9 幻灯片 + 少量高度差异)。
框错目标(圈到墙/只圈半块屏)会让 ar 立刻离群。

**已固化**(`desktop/server.js`):
- 保存时若 GT quad 的 ar 偏离 1.96 超过 0.25 → 状态栏即时提示「⚠ 比例异常 ar=…(没拍全可忽略)」;
- 底部进度点新增**黄色** = 比例可疑(灰=未标 橙=edited 绿=正常 红=noTarget),hover 显示 ar 值。

**边界**:启发式不是判错——没拍全(4282, ar 1.71)、方屏、双屏之一都会合理偏离。
黄点语义是「值得再看一眼」。tolerance 0.25 是让 4282 之外的正常片全绿的经验值。

**复用**:产品端(US-B1 拍后裁剪确认)可加同款提示;server 端 reprocess 后的输出也可做
批量质检(成品 ar 直方图,离群即警报)。

## 2. Display P3 色彩管线:iPhone 照片的两条解码路径不等价

**教训**:同一检测器,浏览器检出正确幕布,Node 评测检出错误候选(IMG_4083 IoU 0.20 vs 1.00)。
根因:iPhone 照片(HEIC/JPEG)带 Display P3 profile,`sips` 烘焙的 PNG 保留 P3;
浏览器解码自动转 sRGB,`spike/png2mat.js` 直接解 PNG 块不做色彩转换 → 像素不同 → 边缘不同。

**已固化**:`eval-run.js` 解码后做 P3→sRGB 矩阵转换(与浏览器对齐),并注释根因。

**复用**:server 端 reprocess(US-J1, sharp)必须显式处理 ICC profile,否则与手机端
(US-C5 语义一致约束)产生系统性漂移。这是 ADR-005 两端一致性的隐藏地雷,已提前排掉。

## 3. 检测器洞察:auto vs screen 的差距在候选评分,不在边缘检测

218 张实测:**auto mIoU 0.906 / screen 0.960**。修正后的 IMG_4083/4282 是活证据:
auto 0.20/0.00,screen 0.97/0.96——检测器「看得见」正确幕布,auto 的评分排序把别的
四边形排前面了。screen 调优的最明确切入点是候选评分先验,不是盲调 Canny 参数。

失败画像(26 张):远距小目标(幕布 <30% 画面)、暗光低对比、幕布被裁/边框不可见。

## 4. 标注工具流程教训

- **提案预放锚定偏差实测 ~2%**(用户接受了看起来对的错提案)——比例校验(第 1 条)是对冲;
- `sips -s format` 不带 `--out` 只警告不转换;`.HEIC` 大写扩展名要兼容;
- `createImageBitmap().close()` 之后 `width/height` 归零——尺寸必须先取;
- `#review=IMG_x,IMG_y` 复审模式:让用户在 221 张里找 4 张是不合理的,URL 直接指定子集;
- 输出用覆盖写,不保留历史版本——「outputs 里只要正确结果」是合理默认。
